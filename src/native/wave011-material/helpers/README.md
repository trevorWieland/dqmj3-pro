# Source-only material constructor component

This subpacket supplies typed C services for the frozen complete constructor. All eight direct helper interfaces, color construction and the common GPU descriptor packing tail now have C implementations. The source-only constructor graph has no retained original instruction dependency. Its owned vtable object is an opaque component identity, not an implementation of the original class's virtual methods.

The graph runs against every frozen constructor fixture without mapping the original executable image into the source execution. All 267 ARM comparisons return and match the complete object and allocation. Its freestanding Windows x64 DLL executes the same 267 cases natively, comparing every logical field and complete storage record after normalizing pointer width. The Windows import directory is empty. The Android ARM64 shared library links without undefined symbols, with four 16 KiB load segments. It has not executed on Android or AYN Thor, and this is not a game build.

Native Windows and Android use a consistent maximum field alignment of four bytes because the original service requests four-byte-aligned runtime storage. The same typed structs contain native pointers. This yields twelve-byte native coordinate generators and a 144-byte Windows material object. Compile-time and exported runtime ABI checks prevent silently using ordinary eight-byte field alignment with that allocation contract. Wire records retain their original scalar widths. GPU addresses remain integer handles in descriptors; they are never dereferenced by this component.

The packing audit found no packed wide member address escaping into a naturally aligned pointer-to-pointer interface and no double fields. The escaping color and word pointers require four-byte alignment. Wide pointer fields are loaded and stored through their declared packed members. The runtime regions have disjoint typed records; byte initialization of the shadow record uses the permitted character alias. The input contract requires initialized untyped allocation or established wire object types, with four-byte alignment. Incompatible externally declared effective types, overlapping mutable aliases, inconsistent packing and alignment below four bytes are unsupported.

The exact object files used in the Android shared library also link into a separate Cortex-A72 CPU-model harness. It runs 534 returning comparisons, covering every fixture at address skews zero and four. The latter places material, heap, context, accessor and storage objects at addresses aligned to four but not eight bytes. Complete normalized state, input/heap guards, stack restoration, floating callee-saved state and Android's reserved x18 are checked. This is execution of actual compiled AArch64 objects in a flat CPU model, not Android device execution. The model records disabled alignment-fault checking. Device memory, alignment-fault-enabled contexts and Android MMU/MTE behavior are outside this evidence. The primary references are [Android NDK ABIs](https://developer.android.com/ndk/guides/abis) and the [Armv8-A memory model guide](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Armv8-A%20memory%20model%20guide.pdf?revision=58b1dd0a-3800-4218-b21a-f95a0332034c).

The heap and texture-resource interfaces are explicit services. The heap returns initialized, exclusive, aligned storage or null. Texture lookup reads immutable name/resource data and may not inspect the incomplete material or its construction allocation. All services in the returning comparisons are deterministic and hash-bound test implementations. Normalized native comparison covers colors, preserved opaque fields, capacities, flags, replacement selection, texture descriptors, transform bits, coordinate generators and projection pointer relations, alpha/blend data, both combiner representations, projection records and font-shadow records. Input and allocation guards are checked.

The storage helper's detailed default header is intentionally defined for this constructor component. The original helper can write transient values derived from unspecified caller-saved floating registers. No standalone equivalence or original source credit is proposed for that allocator. The constructor replaces the complete detailed header before returning. A read-order observer verifies the stronger condition needed here: no helper or deterministic resource service consumes a default byte before its constructor overwrite. It instruments both CPU reads and service API reads. Sixty-nine detailed-material cases exercise the observer; 48 contain genuinely differing transient values at a lookup boundary, and all 28 bytes are overwritten without a prohibited read.

A separately compiled volatile-read mutation returns the same final object and allocation but is rejected for reading a transient field. This proves that final-state equality alone cannot pass the observer. Two other wrong helper sources return normally with different ARM and native Windows state. General callbacks that inspect construction memory, standalone allocator defaults and original class virtual dispatch are explicitly outside this component contract.

The texture helpers preserve the measured format, layout, wrapping and filtering transformations. The qualified domain uses wraps zero through two and filters zero through one. The SDK's wrap value three accesses an unspecified stack slot; it is not approximated. Texture format packing constants are protocol semantics reconstructed from the measured implementation, consistent with the primary GPU definitions already recorded in the frozen material research packet. No third-party implementation is copied or linked, and no original binary payload is embedded.
