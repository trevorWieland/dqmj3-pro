# The supervisor-call class, measured

The corpus drafter can now express an ARM supervisor call. `__svc` is a function
qualifier in armcc 4.1, not a call, and its embedded assembler does not
substitute a macro argument, so the rewrite gives each distinct number a static
helper whose body is one literal `__asm { svc #0x.. }`. At `-O3` the helper is
inlined to the one instruction: `svc #0x3c` assembles to `3c 00 00 ef`.

504 corpus functions contain such a site. This page records what the drafting
pipeline measures when it runs over that whole class. **No function in the
class is newly byte-exact.** The result is not a helper failure: the helper
emits the right instruction. It is a measurement of what the decompiled C does
not contain -- the register interface of the supervisor call.

## Population

```
python toolscripts/corpus_draft_measure.py --prep
python toolscripts/corpus_draft_measure.py --shape svc --order address \
       --minimum 0 --maximum 65536 --out work/drafter/runs/svc
```

`--shape svc` selects every feature-cache record whose decompiled body contains
`software_interrupt(n)` or `SupervisorCall(n)`, without also filtering out data,
literals or control flow. That matters: the class is defined by the call, and a
filter would hide the failure classes this run exists to measure. The 504 count
is a scan of `work/corpus/c` for those two spellings; `--prep` drops the 64
multi-range functions and the 6 functions the baseline build already credits,
which leaves the 434 records the run compiles.

| population | functions | bytes |
|---|---|---|
| corpus functions containing an SVC site | 504 | 66,240 |
| ... whose own original extent contains an `svc` instruction | 469 | 61,560 |
| ... whose extent contains none (Ghidra followed a tail callee) | 35 | 4,680 |
| multi-range functions (two or more original extents; unrepresentable) | 64 | 5,568 |
| already defined and credited by `src/native` | 6 | 244 |
| drafted in this run | 434 | 60,428 |

The 35 without an `svc` in their own bytes are not supervisor-call functions at
all at machine level. Ghidra prints the callee's body in the caller when the
caller is a tail branch; `fn_00735644` is the shortest example. Its 12 original
bytes are `mov r0,#0; mov r1,r0; b 0x0012d6a8` -- a branch into the `svc #0xa`
instruction of the next function -- while its corpus body is only
`software_interrupt(10); return;`. No rewrite of that body can match those
bytes.

Even the easiest shape is zero: 196 clean functions (no data, string, label,

## Failure classes at instruction level

The 108 compared functions were re-placed from the run's `compiled.json` and
unit objects and decoded with Capstone. The classes below are the first way each
departs from the original.

| class | n | what the bytes show |
|---|---|---|
| compiled shorter | 69 | original loads and moves around the SVC have no C object; the compiler deletes them |
| instruction selection, same length | 17 | original spills one argument to the stack; the helper's call boundary moves arguments to callee-saved registers |
| compiled longer | 11 | the helper is treated as a call, so lr (and sometimes r4/r5) is saved; the original SVC is a leaf |
| SVC predicated | 4 | original branches around an unconditional `svc`; compiled keeps the call and predicates it (`svcne`) |
| SVC count changed | 2 | control-flow rewriting removed or duplicated one call |
| compiled SVC absent | 2 | the condition guarding the call is provably false in the reconstructed C |
| corpus SVC absent from original bytes | 2 | tail-call body attributed to the caller |
| pure register allocation | 1 | same instructions in the same order, different register/stack spill |

The 16 compile failures are decompiler shapes no declaration repairs: 12
truncated `LAB_` targets (`#20`), 2 `operand of "*" must be a pointer` (`#75`),
2 `expression must have integral type` (`#31`).

The 310 unrepresentable functions never reach a byte comparison:

| reason | n |
|---|---|
| body calls a coprocessor pseudo-function (`coproc_movefrom_User_R_Thread_and_Process_ID`, `coproc_moveto_Data_Synchronization`, ...) | 261 |
| compiled extent runs past the range the split leaves | 42 |
| reference to a symbol outside the split (`hasExclusiveAccess`, vector conversions, `PTR_FUN_...`, `__switch$$`) | 7 |

Of the 42 extent-past cases, 5 are exactly four bytes long -- the extra literal
pool word that also closed the data-reference band -- and 13 have no length
change at all but a smaller slot. The coprocessor blocker is a separate repair
(the same helper technique may apply to `mrc`/`mcr`), and it is why 261 class
members were not compared. It is not the reason the 108 compared members fail.

## Why the compared members fail

Three short examples carry the whole argument. All bytes are little-endian ARM.

**A leaf becomes a frame.** `fn_00158f14` is 8 bytes in the original:

```
28 00 00 ef 1e ff 2f e1     svc #0x28 ; bx lr
04 e0 2d e5 28 00 00 ef 04 f0 9d e4
                            push {lr} ; svc #0x28 ; pop {pc}
```

The helper call compiles with a frame. So does a literal `__asm { svc #0x28 }`
inside the function, and so does an `__svc(0x28)` function. armcc 4.1 models the
supervisor call as a call: it may clobber lr, so it saves lr. The original was
not produced by that model.

**The argument survives only in the original.** `fn_00108570` is 24 bytes:

```
04 00 2d e5 38 00 00 ef 00 20 9d e5 00 10 82 e5 04 d0 8d e2 1e ff 2f e1
    str r0,[sp,#-4]! ; svc #0x38 ; ldr r2,[sp] ; str r1,[r2] ; add sp,#4 ; bx lr

30 40 2d e9 00 40 a0 e1 01 50 a0 e1 38 00 00 ef 00 50 84 e5 30 80 bd e8
    push {r4,r5,lr} ; mov r4,r0 ; mov r5,r1 ; svc #0x38 ; str r5,[r4] ; pop {r4,r5,pc}
```

The original saves only the first argument, to the stack, and keeps the second
in `r1` across the call. The reconstructed C (`svc_0x38(); *param_1 = param_2;`)
forces both into callee-saved registers. A `__svc(0x38)` helper called with the
same two arguments was compiled as an alternative and also moved both into
callee-saved registers. The register contract the original compiler used -- which
registers an SVC preserves -- is not present in the corpus and not expressible
with this compiler.

**The lost setup is deleted, not rescheduled.** `fn_00147e54` is 24 bytes:

```
30 00 2d e9 08 40 9d e5 0c 50 9d e5 22 00 00 ef 30 00 bd e8 1e ff 2f e1
    push {r4,r5} ; ldr r4,[sp,#8] ; ldr r5,[sp,#0xc] ; svc #0x22 ; pop {r4,r5} ; bx lr

04 e0 2d e5 22 00 00 ef 04 f0 9d e4
    push {lr} ; svc #0x22 ; pop {pc}
```

The two loads feed registers that only the supervisor call can read. Nothing in
the decompiled body names them, so C marks them dead and the compiler removes
them. This is the 69-function class: the draft is not a differently scheduled
version of the original, it is missing instructions the decompiler could not
represent as C.

## What this closes

The SVC class is closed for this pipeline on the measured armcc 4.1 build 1454
profile: the helper can spell the instruction, but the corpus cannot spell what
the instruction does to the registers, and armcc's call model produces a frame
and a different register allocation. No declaration, no address and no rewrite
of the decompiled body changes that. Reopening it would need source evidence
the corpus does not carry -- the register inputs and preserved registers of each
SVC site -- or a compiler that models an SVC as a leaf instruction. Shipping an
assembly stub for each site would be original-assembly reconstruction, not a
corpus draft, and is outside this measurement.

The 64 multi-range functions and the 261 coprocessor-blocked functions are not
counterexamples: the first cannot be one contiguous object under this
measurement, and the second were never compared. Repairing the coprocessor
pseudo-functions is a separate lever; it does not supply the missing register
interface, which is why it was not attempted here after the SVC subset measured
zero.
