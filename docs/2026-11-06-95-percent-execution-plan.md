# Validated source coverage and native platform execution

The active objective is to reach 95 percent confirmed and validated source coverage and working native Windows and modern Android game builds, including AYN Thor and other dual-screen handhelds. This remains a full game objective. Recovered-function runners, crosscompiled libraries, original-code roundtrips and emulator wrappers cannot satisfy the game-build requirements.

The owner selected an independent public/open-toolchain approach. Clang/LLVM, public system documentation, measured original-code oracles and our own tooling are the supported foundation. ARMCC archives are optional calibration research, and neither paid compiler access nor proprietary SDK material is an execution prerequisite. This decision preserves the source and validation requirements rather than changing their meaning.

## Source coverage requirements

Keep complete native program/module identities, interpreted programs, original embedded source, shader programs and unresolved executable formats distinct. The update executable is the initial native target; the base remains a separate reference build. Complete the executable inventory before publishing an overall source percentage. Gross initialized native segment bytes provide a conservative known-module measurement; they are not a reviewed executable-only denominator or an overall game percentage.

Each reconstructed source interval needs ordinary readable C/C++, frozen source and compiler configuration, complete instruction/pool/relocation extents, caller/boundary corroboration, genuine linked output, original-code comparisons, appropriate compiled wrong-source controls and an independent committed-tree replay. Historical compiler identity and the identity of a measured compiler that happens to produce an exact match are different claims. Clang matches can be admitted with their measured profile without claiming Clang built the original game.

Source acceptance is serialized by the coordinator. Count only disjoint physical intervals from finalized receipts. Alias labels, duplicate object functions, regenerated linkage and retained original gaps never add another byte. Original script text contributes to a separate source-availability inventory and receives zero newly reconstructed-source credit. Behavior-only drafts remain available for engine understanding and portability testing, without exact-source credit.

The 95 percent requirement stays unproved while any overall denominator or major executable category remains unresolved. Source-only native executable and game/container construction, source readability, independent replay and platform execution remain separate gates.

## Parallel execution

The available capacity is one coordinator and three workers. The native lane reconstructs coherent source families; the inventory lane identifies executable regions, functions and native/script interfaces; the platform lane builds and tests the recovered sources on Windows and Android. Workers own disjoint files and output roots. Completed lanes receive the next useful independent task. No worker result self-publishes accepted coverage.

Frozen packets include source/tool/input hashes, canonical program/module/address/mode, complete extents, ABI/types, read/write dependencies, explicit unsupported behavior, reproduction commands, negative controls and requested credit. Shared publication and aggregate checks run only after relevant source inputs stop changing. Preserve failures and runnable committed snapshots so subsequent turns can move directly to the next family.

## Integration and platforms

The module linker uses original gap sections only as explicit zero-credit scaffolding. Reconstructed C functions are genuinely linked at their original addresses, and the complete resulting native image is compared with the pinned input. This is an integration gate; a hybrid image does not establish a source-only game.

The Windows track must progress from native source-function execution to real engine services and a playable source-built game. The Android track must progress from ARM64 compilation to a packaged application, device execution, lifecycle correctness and game behavior. Modern Android alignment, ABI, resource packaging and all dependencies require qualification. An APK label or a successfully linked shared library is insufficient.

AYN Thor validation requires measured display enumeration, one engine simulation with two logical views, correct controller/touch routing, surface loss and activity lifecycle handling, suspend/resume and save restoration. Maintain a single-display fallback for other devices. Record actual device/firmware evidence; hardware capabilities do not prove an application works on that hardware.

## Current next work

The current source frontier is the actual object and engine graph. Frozen compact prototypes, common reference prefixes, native/script closures, weak references, strings and arrays provide typed ownership. Closure creation still has declared lookup/error boundaries. The actual table provider has independent native topology checks; the remaining table helpers and broader lookup/metamethod/error paths continue in separate frozen lanes. The owning rule-file family is closing real SDK/filesystem-provider paths rather than replacing unrecovered game helpers with test stubs.

The coordinator keeps exact linked-source receipts separate from the bounded working-C catalog. Each completed family receives a fresh committed-tree replay, explicit platform fixture restrictions, publication audit, default-branch CI and hosted source-link verification. Generated names headers expose descriptive APIs while compiler-only aliases preserve historical legacy verification binaries.

Inventory follow-up retains mixed ARM/Thumb transfer witnesses, shared tails and indexed data as explicit ownership problems. Unknown executable categories and unclassified text remain in scope. Windows/Android component execution and dual-view presentation are established component gates; source-only whole-VM execution, gameplay, complete game packaging and physical AYN Thor validation remain outstanding.

Continue independent source families in all three worker slots, prioritize closing the actual VM/game graph, and publish verified batches. Status narration, source-only compilation or partial interpreter checkpoints do not satisfy the active objective.
