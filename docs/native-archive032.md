# Game resource archive and decompression lane

The measured XBB view is used by actual model and environment resource callers. `0x26f918` formats a BCH resource name, constructs the archive view, obtains its named member size and queues loading through `0x337680`. `0x277e84` loads field environment XBB members zero and one. A separate caller, `0x238fec`, prepares a gzip wrapper, allocates decoded output, then creates an XBB view and finds a named member. These are observed call graphs, not claims that startup, resource jobs or rendering are already reconstructed.

The first sub-batch covers thirteen inventoried ARM bodies totaling 992 instruction bytes. Name lookup `0x183688` includes its complete second body range at `0x1912bc`. The separate deleting-destructor candidate at `0x5f5d14` owns 36 instruction bytes and a four-byte pool. Its exact two-slot table prefix, publication witness, tail-free call and absence of existing owners are recorded for coordinator review; it is not silently added to the canonical census.

XBB has a 32-byte header, sixteen-byte member records and an eight-byte sorted key/index trailer in modes zero and one. Other mode words use linear record-key lookup. The seed lives at header offset twelve. The signed-byte name hash uses an arithmetic shifted contribution, not a conventional rotate for negative characters. Collisions compare only the hash; sorted search preserves midpoint selection. Raw sorted lookup may return an out-of-range trailer index, while member accessors apply the count bound. A zero-count sorted lookup still probes declared backing bytes. Generated fixtures preserve these behaviors instead of adding a new validation policy.

The view owns a separately allocated one-pointer holder; it borrows the archive bytes. The target/native holder requests are four/eight bytes, with corresponding pointer alignment. Destruction releases the holder, and deleting destruction then releases the outer view. Archive data is read-only as consumed by these functions; later BCH relocation may mutate an independently owned backing buffer. No global immutability claim is made. A null bind checks the old image and clears its pointer on success. Null holder/name and arbitrary out-of-bounds payload offsets are not converted into invented safe errors.

The original oracle executes the measured original instructions, including real SDK allocation/free wrappers, against an explicit typed platform heap. The fixture supplies the observed ready flag and current-heap state; it does not claim to reconstruct SDK startup or allocator internals. Source ARM, Windows and high-address AArch64 execute only authored C. Every backing byte is compared after typed pointer and physical holder-width translation, with immutable inputs, outer guards, release order and preserved ABI state checked. Source does not map an original executable image. The AArch64 CPU model does not establish Android OS/device behavior.

The new reference mapper groups contiguous ExHeader segments to avoid thousands of individual Unicorn map calls. A separate check compares every mapped original byte, BSS, padding and permission against the frozen page mapper. Original bytes are unchanged. Earlier slower exploratory runs remain private and are not labeled unchanged-input replays.

The reachable gzip wrapper explicitly passes windowBits 31, stream size 56 and compatibility string `1.2.7.f-NINTENDO-CTR-SDK-v1`; it calls inflate with flush four twice and accepts only the second result one. Output sizing, ownership and cleanup must be qualified separately from equal decoded bytes. Public zlib 1.2.7 is a distinct portable dependency with its own archive/source/license lock. Its public sources do not establish Nintendo fork identity or grant underlying SDK/inflate recovery credit. The shared tool lock remains unchanged.

Remaining game dependencies include resource file ownership/IO, gzip wrapper completion, BCH relocation/construction, resource-job scheduling, graphics initialization and renderer integration. Original assets and executable material stay private; public fixtures contain generated synthetic data and hashes.
