# Container and packaged-program audit, wave 003

This audit structurally classifies all 13 archive layouts left unresolved by inventory wave 001. It also identifies verified embedded DSP firmware and additional GPU shader images. It adds no recovered-source credit and does not lock either the native or overall executable denominator.

Both owner CIA hashes are verified before and after inspection. Every NCCH content is streamed and compared with its frozen content/TMD hash; NCCH headers and unencrypted flags are checked. Actual RomFS and ExeFS file tables must match the existing inventory. Each consumed top-level file is size/hash checked. Main executable bytes are freshly expanded from the verified CIA ExeFS entry with the qualified reader and compared with the frozen decompressed-image hash; generated code.bin files are not input dependencies.

The base has 32,594 payload occurrences and 26,759 unique payloads; the update has 3,217 occurrences and 2,218 unique payloads. These include ExeFS entries and expanded main images, beyond wave 001's 26,755/2,215 RomFS/nested payload counts. No previously supported nested payload family is dropped. The final recognized SARC/XBB/gzip paths have zero decoder errors.

All 1,573,413,996 base RomFS file bytes and 11,066,345 update RomFS file bytes receive signature coverage. Reports separate direct signature searches of unique payloads from SHA-256-verified alias inheritance. The only unbuffered unique payload is the base's 360,002,432-byte fieldPack XBB; it is streamed in chunks with overlap, and its bounded children are inspected individually. Occurrence and recursive byte sums overlap physical storage and must not be used as a global physical coverage percentage.

The old bounds remain: recursion depth five, buffered member size 32 MiB and total expanded gzip output 128 MiB. Gzip accepts one bounded complete stream and rejects truncation, overexpansion and trailing streams. Unknown/custom compression remains opaque. Metadata, padding and wrapper areas outside named payloads are hash verified but not all semantically interpreted; `findings.json` reports gross physical region extents and those residual areas explicitly.

The 13 LodSize indices contain 1,044 records and 25,472 bytes of metadata. Every one has mode word one, zero name pointers, nonzero record lengths, contiguous virtual offsets starting at zero, and a sorted eight-byte key/index lookup permutation following its sixteen-byte record table. Its file ends exactly after those tables. Thus its large virtual ranges are detached descriptions rather than invalid physical payload extents. The index contains zero member payload bytes.

Mode word one alone does not imply detachment. The EventFlagTbl and SoundTbl archives use the same nameless lookup form with ordinary internal data after their tables. The qualified parser distinguishes these by complete metadata and payload extents. An early stricter interpretation reduced known coverage; that limitation was corrected and guarded by a separate internal-mode-one control before final evidence publication.

All 1,044 detached records match complete same-scope BCH sibling sequences by stored order and exact sizes. Eight sets are actual RomFS siblings; five are internal siblings in the test fieldPack archive. The 154 distinct lookup keys have no conflicting inferred basename hashes across these matches. This corroborates a key/name relationship but does not prove the name-hash algorithm or the game's runtime resolver. Repeated equal-size siblings are not presented as an independently resolved hash lookup. Developer build paths from internal archive names are not published; names are retained only as hashes in metadata.

Base/update comparison observes 88 shared physical paths: 14 have identical hashes, 74 differ. There are 13,472 base-only and 37 update-only content-zero RomFS paths. The update has none of these detached indices. These are physical comparisons; runtime overlay, precedence and fallback behavior remain unproved.

Both decompressed main images embed the same 49,772-byte DSP1 firmware, SHA-256 `96f3962838ebe92a9e99d0b078ade3673b9b2f243ebec0474d3e49a92b655b85`. Its container starts at file offset 7,831,268 in base and 7,840,060 in update; the DSP1 marker is 256 bytes later. Both lie in initialized rodata. All five segment extents and embedded SHA-256 values verify: 43,748 bytes target DSP program memory and 5,256 bytes target DSP data memory. The RSA signature is not independently verified. This is a distinct executable category, not newly recovered ARM source.

The base contains 46 structurally validated DVLB/DVLP code images totaling 52,476 code bytes and 76 DVLE executable entries. Thirty images occur inside main-module rodata; the remaining sixteen occur in the two shader BCH files and four standalone SHBIN files. The update contains the same thirty main-module code images, totaling 33,012 bytes and thirty entries. All thirty update code hashes occur in base; sixteen code images occur only in base. Code sections, operand tables and declared entry intervals are checked, while instruction semantics and complete GPU runtime state are not reconstructed.

The audit checks section extents and command packet framing in 4,578 unique base BCH payloads and 21 update BCH payloads. No shader-transfer payload was identified in those qualified command sections. This does not exclude shaders in BCH raw sections: twelve DVLB images are separately found in the two shader BCHs. BCH relocations, object graphs, shader binding and complete PICA register semantics remain open.

Full payload searches include CRO0/CRS0/FIXD with their expected 0x80 prefix, ELF32 headers, NCCH, CRR0, FIRM, DSP1 at its 0x100 header position, and DVLB anywhere in inspected bytes. There are no additionally qualified CRO-layout, ELF32 or NCCH program candidates in the payload scan. Nine base marker-only hits remain explicitly unqualified; update's candidates are the thirty shaders and DSP firmware. A marker without a valid structure receives no program or source credit. Raw unmarked code remains possible.

Compiled-VM prefix checks use the actual imported public Squirrel 2.2.5 sources: the 0xFAFA unsigned-short stream tag, SQIR head, serialized SQChar width, and PART function prefix. Integer widths four/eight, character widths one/two/four and both byte orders are searched. No matching prefix appears in the inspected streams. This is not a universal absence proof for custom, compressed, headerless or modified bytecode. No game bytecode is loaded into a VM.

Eleven controls cover detached and internal mode-one XBB, invalid lookup/offset/name/mode/truncation, gzip bounds/trailing streams, overlapping extent accounting, exact public serialization tags, a long serialization prefix crossing a streamed chunk boundary, PICA packet extents and DSP segment digest rejection. Synthetic controls contain no game payloads.

The output consists only of metadata, hashes, extents and reproduction records. Unrecognized leaf formats, unknown compression, raw native code, unresolved key/name lookup behavior, incomplete GPU object graphs and hash-only wrapper regions keep inventory completeness open. A coordinator may review the closed structural issues separately from any denominator decision.
