# Reconstructed material construction in the measured scene

This component feeds actual owner NaviMap SARC, FLYT and BFLIM resources through the frozen reconstructed material constructor and its source helpers. All 19 material records are constructed. Every renderer material field comes from the returned typed object: colors, texture bindings, samplers, transforms, coordinate generators, projections and detailed combiner data. The wire parser validates the bounded measured profiles before construction. It does not provide the material values used for rendering.

All 17 picture/material cases render. The two texture-free font materials are constructed but are outside the picture renderer. Fonts, parts, animation and an upper gameplay scene remain unimplemented. The two views mirror the measured static map as a lifecycle/input integration component. This is not a full game or new original-source credit.

The heap uses exclusive caller-owned memory, initialized and allocated by the source bump service. Windows supplies untyped VirtualAlloc memory. Android retains a direct ByteBuffer and passes its address through JNI. The minimum alignment is four bytes, with a consistent four-byte maximum field alignment for the internal material/render structs. The Win32 and JNI boundary files keep their natural platform ABI and exchange only scalar values or raw buffer pointers. In particular, Win32 structs and addresses passed to pointer-to-pointer OS interfaces are not compiled with the internal packing option.

Serialized names and material records are copied into aligned foreign allocation before the typed constructor reads them. The supported storage contract is untyped allocation or correctly established compatible object types; incompatible declared effective types and concurrent access are unsupported. Input archives and published scene memory cannot alias the constructor arena. Allocation checks precede writes. A new import resets the private construction epoch; no SDK pointer survives in published state. The source allocator release callback is a no-op within that epoch, and no standalone SDK allocator behavior is proposed.

The resource service binds actual BFLIM formats and logical decoded dimensions to software texture handles. Its resources describe canonical logical images after decoding, with orientation zero and no alternate mip image. These handles are not original GPU physical addresses. Original texture-loader, uploader and hardware rendering equivalence are not claimed. The lookup callback compares its immutable name bindings and returns an immutable resource descriptor. It does not inspect incomplete constructor storage. Renderer conversion starts only after the constructor returns, preserving the frozen transient-field contract.

Successful imports publish geometry, an 80-word scalar audit for every material, and complete pixels in one bank swap shared by both views. Failed materials, textures, unsupported shader operations, aliased memory and heap exhaustion retain the old generation, material audits, geometry, pixels and controls. The heap-exhaustion test fails after the first of two constructors completes. A compiled wrong constructor returns normally and renders all 17 pictures, but its changed colors produce a framebuffer rejected by the independent reference. This demonstrates that the reconstructed constructor drives rendering.

The actual Windows executable executes the owner archive through the recovered resource queue and checks 192,000 GDI RGB pixels, including letterboxes and both views. All 19 complete constructed objects and their full logical allocations match original ARM constructor execution supplied with the same actual asset-derived descriptors. The original GPU code is used only by private verification. It is absent from the Windows and Android component artifacts.

An independent float64 homogeneous-matrix/vector renderer parses all 35 panes and 17 pictures. It consumes material state from original constructor execution and BFLIM pixels decoded independently of the application. Its full 76,800-pixel RGBA output matches every application channel exactly. Both produce SHA256 a74899cd252016021bfb153e1cb98710b065725fd8e3868ca077d46043a94114. The independent tools are verification-only pinned NumPy and texture2ddecoder wheels. Neither is packaged or linked into an application. NumPy uses its BSD-3-Clause license and bundled notices; texture2ddecoder is MIT. Their wheels and effective module hashes are recorded locally. The primary package reference is [NumPy 2.3.4 on PyPI](https://pypi.org/project/numpy/2.3.4/).

The actual Android object files also execute in a separate Cortex-A72 flat CPU model. Both views and the complete published material audits match the original-qualified Windows results and independent framebuffer. Archive and arena addresses are above four GiB, with the arena aligned to four but not eight bytes. The heap and resource services execute as compiled C, without emulated allocator or lookup callbacks. The model also exercises late import rejection, secondary touch and pause behavior. It verifies callee-saved integer/VFP state, stack restoration and Android's reserved x18. This does not execute Android, the activity lifecycle, a device or AYN Thor.

The APK is ARM64, targets API36 with minimum API29, has verified signatures and uncompressed native code aligned to 16 KiB in both ELF load segments and the ZIP. It contains no original assets. The source activity uses SAF import, app-private atomic caching, display enumeration, a Presentation view, generation-tagged surfaces, one primary clock and logical controller/touch routing. Device behavior remains unverified. The applicable primary documentation is [Android 16 KiB page support](https://developer.android.com/guide/practices/page-sizes), [Android ABIs](https://developer.android.com/ndk/guides/abis), [Presentation](https://developer.android.com/reference/android/app/Presentation) and [SAF](https://developer.android.com/training/data-storage/shared/documents-files).
